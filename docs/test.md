## 1. What you are testing

You evaluate **two scheduling algorithms** on a **custom load balancer**:

| Algorithm | Code location | What it does |
|-----------|---------------|--------------|
| Round Robin | `load-balancer/src/schedulers/roundRobin.js` | Rotates evenly: server1, server2, server3, server1, ... |
| Least Connections | `load-balancer/src/schedulers/leastConnections.js` | Sends each request to the server with fewest active requests |

You also **validate** those algorithms against **Nginx** (same idea, different engine):

| Nginx mode | Config file | Host port |
|------------|-------------|-----------|
| Round Robin | `nginx/round-robin.conf` | `http://localhost:8081` |
| Least Connections | `nginx/least-conn.conf` | `http://localhost:8082` |

**Traffic** is generated by **k6** scripts in the `k6/` folder.  
**Results** come from the load balancer metrics export and from k6 summary JSON files.  
**Charts** are produced by `python/analyze.py`.

## 6. How metrics runs work (important)

There are **two layers** of results:

### Layer 1: Custom load balancer recording (detailed)

When a **metrics run is active**, the engine records every proxied request to disk:

- Folder: `metrics/runs/<runId>/`
- Files: `requests.csv`, `requests.json`, `resources.csv`, `summary.json`

You start and stop a run with either:

- the **dashboard** (Algorithm Control page), or  
- the **API** (curl), or  
- **`run-matrix.sh`** (does this automatically for custom engine trials)

**Without starting a run**, traffic still works, but you will **not** get a saved experiment folder for the dashboard Results page.

### Layer 2: k6 summary (client-side)

Every k6 run can write a summary JSON (latency, throughput, error rate as seen by k6).  
The matrix script writes these under `metrics/k6/`.

### Manual start / end of a metrics run (API)

**Start:**

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/start \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"round-robin","scenario":"steady","engine":"custom","notes":"trial 1"}'
```

**End (saves files under `metrics/runs/`):**

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/end \
  -H 'Content-Type: application/json' \
  -d '{}'
```

### Switch algorithm (API)

```bash
# Round Robin
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"round-robin"}'

# Least Connections
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"least-connections"}'
```

Valid names are exactly:

- `round-robin`
- `least-connections`

## 9. How to run any k6 test file

### 9.1 General pattern

Always run k6 from the **project root** so paths resolve:

```bash
cd /home/spectre/Documents/Works/Projects/eben

k6 run \
  -e TARGET_URL=http://localhost:8080 \
  -e ALGORITHM=round-robin \
  -e ENGINE=custom \
  k6/steady.js
```

| Flag / env | Meaning |
|------------|---------|
| `k6 run` | Execute a test script |
| `-e TARGET_URL=...` | Base URL of the system under test (load balancer or Nginx) |
| `-e ALGORITHM=...` | Label only (tags k6 output); does **not** switch the custom LB by itself |
| `-e ENGINE=...` | Label only (`custom` or `nginx`) |
| last argument | Path to the script file |

**Important:** Setting `-e ALGORITHM=least-connections` only **tags** the k6 report. To actually change the custom engine algorithm, you must call the API or use the dashboard (or use `run-matrix.sh`, which does both).

### 9.2 Optional k6 environment overrides

These work on the scripts that read them:

| Variable | Used by | Default | Example |
|----------|---------|---------|---------|
| `TARGET_URL` | all | `http://localhost:8080` | `http://localhost:8081` |
| `VUS` | steady, failure | 20 or 25 | `VUS=40` |
| `DURATION` | steady, failure | `60s` or `90s` | `DURATION=30s` |
| `SLEEP` | steady, ramp-up, failure | `0.1` etc. | `SLEEP=0.05` |
| `PEAK_VUS` | ramp-up | 40 | `PEAK_VUS=60` |
| `BURST_RATE` | burst | 80 / 100 | `BURST_RATE=50` |
| `WORKLOAD_PATH` | all | `/api/work` | usually leave default |

Example shorter steady test:

```bash
k6 run -e TARGET_URL=http://localhost:8080 -e VUS=5 -e DURATION=15s k6/steady.js
```

### 9.3 Save a k6 summary to a file

```bash
mkdir -p metrics/k6

k6 run \
  -e TARGET_URL=http://localhost:8080 \
  -e ALGORITHM=round-robin \
  -e ENGINE=custom \
  --summary-export=metrics/k6/custom_round-robin_steady_manual.json \
  k6/steady.js
```

### 9.4 Your test files list

| File | What it simulates |
|------|-------------------|
| `k6/steady.js` | Constant number of users for a fixed time |
| `k6/ramp-up.js` | Users climb, hold peak, then drop |
| `k6/burst.js` | Arrival-rate spikes (bursty traffic) |
| `k6/failure.js` | Steady traffic while you kill one backend |
| `k6/run-matrix.sh` | Runs many combinations automatically |
| `k6/lib/helpers.js` | Shared helpers (not run alone) |

## 10. Test C: Steady load (`steady.js`)

**Purpose:** Constant load. Compare Round Robin vs Least Connections under stable traffic.

**Default load:** 20 virtual users for 60 seconds.

### End-to-end steps (manual, with detailed metrics)

1. Ensure Docker stack is up (Section 4) and healthy (Section 5).

2. Set algorithm to Round Robin:

```bash
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"round-robin"}'
```

3. Start a metrics run:

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/start \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"round-robin","scenario":"steady","engine":"custom","notes":"RR steady trial 1"}'
```

4. Open the dashboard (optional) at http://localhost:5173 and watch **Live Monitor**.

5. Run the test from project root:

```bash
cd /home/spectre/Documents/Works/Projects/eben
k6 run -e TARGET_URL=http://localhost:8080 -e ALGORITHM=round-robin -e ENGINE=custom k6/steady.js
```

6. When k6 finishes, end the metrics run:

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/end \
  -H 'Content-Type: application/json' \
  -d '{}'
```

7. Repeat steps 2–6 for Least Connections, changing names:

```bash
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"least-connections"}'

  -H 'Content-Type: application/json' \
  -d '{}'
```

8. Check results:

- Browser: **Results** page on the dashboard  
- Disk: `ls metrics/runs/`  

For a dissertation, run **at least 3 trials** per algorithm (change the notes each time).

## 13. Test F: Single server failure (`failure.js`)

**Purpose:** One backend dies mid-test. You observe health checks, redistribution to remaining servers, and error rate.

This test needs **two terminals** and Docker container names from Compose.

### End-to-end steps

1. Stack must be up with Compose (so containers are named `eben-backend-1`, `eben-backend-2`, `eben-backend-3`).

2. Set algorithm (example: Least Connections):

```bash
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"least-connections"}'
```

3. Start metrics run:

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/start \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"least-connections","scenario":"failure","engine":"custom","notes":"stop backend-2 mid run"}'
```

4. **Terminal 1** – start k6 (default ~90 seconds):

```bash
cd /home/spectre/Documents/Works/Projects/eben
k6 run -e TARGET_URL=http://localhost:8080 -e ALGORITHM=least-connections k6/failure.js
```

5. **Terminal 2** – about **20 seconds** after k6 starts, stop one backend:

```bash
docker stop eben-backend-2
```

6. Watch the dashboard **Live Monitor**: `server-2` should become **Unhealthy** after a few health-check intervals. Traffic should go to the remaining healthy servers.

7. About **40 seconds later**, restore the server:

```bash
docker start eben-backend-2
```

8. When k6 finishes, end the metrics run:

```bash
curl -s -X POST http://127.0.0.1:8090/api/metrics/run/end \
  -H 'Content-Type: application/json' \
  -d '{}'
```

9. Repeat the whole procedure for **Round Robin** if you need both algorithms under failure.

**Note:** `run-matrix.sh` does **not** automate this scenario. You always run failure tests manually.

Nginx does not use your control API metrics runs. You rely on **k6 summaries** for Nginx, and compare to custom-engine k6 or custom `summary.json` files.

## 22. Troubleshooting

| Problem | What to do |
|---------|------------|
| `curl: Connection refused` on 8080 | Stack not up. Run `docker compose ps` and `docker compose up --build` |
| k6 `connection reset` / many failures | Backends overloaded or down. Lower VUs; check `docker compose logs` |
| Dashboard stuck on "Reconnecting" | Control API not on 8090; check `docker compose logs load-balancer` |
| Results page empty | You never ended a metrics run, or volume not mounted. End run with API/dashboard; confirm `metrics/runs/` has folders |
| Algorithm tag in k6 does not match routing | You only set `-e ALGORITHM=...`. Also call `PUT /api/algorithm` or use the dashboard |
| `run-matrix.sh: k6: command not found` | Install k6 (see `docs/installation.md`) |
| `python: No module named pandas` | Activate venv and `pip install -r python/requirements.txt` |
| Nginx works but custom LB 503 | All backends marked unhealthy. Check health: `curl http://127.0.0.1:8090/api/servers` |
| Permission denied on `run-matrix.sh` | `chmod +x k6/run-matrix.sh` |
| Want a 15 second practice test | `k6 run -e VUS=3 -e DURATION=15s k6/steady.js` |

## Quick copy-paste: first successful practice loop

If you only want to see **one complete loop** once the stack is up:

```bash
cd /home/spectre/Documents/Works/Projects/eben

# 1) Algorithm check
node load-balancer/scripts/verify-schedulers.js

# 2) Use Round Robin + record metrics + short load
curl -s -X PUT http://127.0.0.1:8090/api/algorithm \
  -H 'Content-Type: application/json' \
  -d '{"name":"round-robin"}'

curl -s -X POST http://127.0.0.1:8090/api/metrics/run/start \
  -H 'Content-Type: application/json' \
  -d '{"algorithm":"round-robin","scenario":"steady","engine":"custom","notes":"practice"}'

k6 run -e TARGET_URL=http://localhost:8080 -e VUS=5 -e DURATION=20s k6/steady.js

curl -s -X POST http://127.0.0.1:8090/api/metrics/run/end \
  -H 'Content-Type: application/json' \
  -d '{}'

# 3) See saved run
ls metrics/runs/

# 4) Optional: open dashboard Results at http://localhost:5173/results
```

That sequence is the core of almost every custom-engine test: **set algorithm → start run → run k6 file → end run → inspect results**.
